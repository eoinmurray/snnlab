Combine snnlab's spiking network with ordinary PyTorch layers in one trainable model. This example reuses **`examples/training/network.bundle`** and trains fresh weights for the same task: recognise which pair of four input channels is more active.

The saved bundle supplies the spiking architecture, trainable parameter names, learning rates, constraints and surrogate configuration. Its two output values feed an external **Linear(2, 8) → ReLU → Linear(8, 2)** head, defined with ordinary PyTorch modules. PyTorch handles batching, loss calculation, backpropagation, optimizer steps, evaluation and saving weights. There are no calls to `snnlab.sim.execution.train`, `simulate` or `infer`.

![Hybrid classifier: the saved spiking network produces two features, followed by an ordinary PyTorch head with Linear 2 to 8, ReLU, and Linear 8 to 2 layers producing final class logits.](/pytorch/network.png)

Unlike [Inference](/inference), this example does **not** load Training's `trained.checkpoint`. It starts a new training run using the same architecture and initialization rules. Its outputs live separately in `examples/pytorch/`.

The model accepts `(batch, time, 4)` spikes. The saved SNN's `class_scores` output has shape `(batch, 2)`; here those two values serve as features for the external head. `Linear(2, 8)` creates eight hidden features, `ReLU` applies a nonlinearity, and `Linear(8, 2)` produces the final class logits. The bundle remains unchanged.

Both `snn` and `head` are registered child modules. `model.parameters()`, `.to(DEVICE)` and `state_dict()` therefore include the SNN and the ordinary PyTorch layers. The full script includes the `make_diagram` rendering helper used above.

The recipe explicitly identifies trainable parameters and the fast-sigmoid surrogate slope. Discrete spike thresholds remain in the forward pass; surrogate derivatives allow PyTorch autograd to carry gradients through the E neurons to the input weights.

The external head is defined in Python, outside the snnlab graph. Replace it with other PyTorch layers as needed. For richer features, declare a larger feature output before compiling a different bundle. Call the module directly while training: `.numpy()` and detached diagnostics are for analysis, not for constructing a differentiable loss.

## 4. Configure ordinary PyTorch optimization

```python
{{OPTIMIZER}}
```

`parameter_map()` gives the module's live parameters under their original graph names. The recipe supplies separate learning rates for input-to-E weights and `w_out`; frozen groups, if any, are excluded. A separate optimizer group explicitly adds `model.head.parameters()` at `HEAD_LEARNING_RATE`. `nn.CrossEntropyLoss` consumes the final head logits and integer labels. Omitting the head group would leave its weights untrained.

This loop mirrors the supplied recipe's cross-entropy objective and AdamW optimizer. The recipe is data, not an automatically executed PyTorch training program. If you change its objectives or add regularizers, implement those calculations in your external loop too.

`non_negative` selects constrained weights from the graph. Your optimizer does not know snnlab's constraints: this example enforces them explicitly after each step. The signed readout weights and ordinary PyTorch head are left unconstrained.

Each minibatch follows the usual sequence: clear gradients, forward, calculate loss, backward, clip gradients and step the optimizer. The final block clamps non-negative weights. The loss backpropagates through the head into `w_out`, then through surrogate spike derivatives into `w_in`. All connections learn together. Gradient clipping includes both child modules.

Epoch 0 evaluates the initialized network. Subsequent rows evaluate both complete splits after each epoch, with sample-weighted loss and classification accuracy. These measurements use fixed weights rather than averaging losses from changing weights during training.

The shuffled orders can differ from snnlab's built-in trainer because this example uses a PyTorch `DataLoader` generator. It demonstrates the same task and optimization settings, without requiring identical training trajectories.

`trained.pt` contains both the SNN and external head weights and biases in one ordinary `state_dict`. Reconstructing the same wrapper from the bundle provides matching parameter names and shapes; `load_state_dict` restores the learned values. The example checks that reloaded weights exactly match and measures performance on the separate test split.

This file saves weights only. It is distinct from snnlab's `trained.checkpoint`, and does not contain optimizer state or resume coordinates. To resume your own loop, save its optimizer and other training state separately. The saved bundle remains necessary to reconstruct the architecture.

## 10. Integration boundaries

The current interface is `GraphExecutor`, not a `lang.to_torch` conversion function. It executes the supported compiled graph using PyTorch operations and the snnlab spiking implementation; it does not export a dependency-free network.

Inputs to the executor are named tensors, and its direct result is an `ExecutionResult`. The wrapper adapts these to your application's tensor interface. Each call starts with fresh dynamic state unless continuation state is explicitly supplied. Returned continuation state is detached, so gradients do not span separate continued calls.

Declared outputs retain gradients. Exposed diagnostics are detached, and `result.numpy()` produces detached copies. When training a custom PyTorch head, use tensor outputs directly and declare the features it needs with `net.output` before compiling the bundle.
