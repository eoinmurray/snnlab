---
title: Performance and Custom Components
description: Write tensor callbacks for compilation, understand CUDA replay safety, and check which performance paths your custom components actually use.
---

Custom components can use compiled tensor kernels, eligible CUDA Graph replay,
automatic precision and input prefetch. Support depends on the callback and the
execution mode. `Performance()` requests the automatic defaults; it does not
guarantee that every optimization applies to every component.

The [Custom Neurons and Synapses example](/custom-neurons-and-synapses) provides
importable, vectorized neuron and synapse callbacks, deterministic state
initializers and explicit capture-safety declarations. The
[Performance reference](/api/sim/execution-spec#performance) lists every field,
default and validation rule; [Extensions](/api/lang/extensions) defines callback
signatures and portable registration.

## What each performance setting does

| Setting and default | Relation to custom components |
| --- | --- |
| `compile_mode="default"` | Compiles compatible custom neuron/synapse updates, operations, surrogate derivatives and post-update constraints. No decorator is needed. Objectives, regularizers, encoders, optimizer factories, initializers and scalar modulation callbacks remain outside this runtime compilation scope. Compiler errors surface explicitly. |
| `compile_block_steps="auto"` | Targets CUDA 16 / MPS 4 / CPU 1 timesteps per block. Registered custom neurons, synapses and surrogates currently fall back to the individual-kernel loop. Their tensor kernels still compile. `capture_safe=True` does not remove this block limitation. Other graph features can also force fallback. |
| `cuda_graphs="auto"` | Eligible repeated CUDA work can capture custom tensor callbacks declared `capture_safe=True`. Training captures forward/loss/backward; optimizer steps, clipping, constraints, reporting and persistence remain outside capture. Forward-only replay requires execution without autograd. |
| `precision="auto"` | Uses supported native CUDA BF16 autocast with float32 parameters and high matmul precision/TF32. Custom callbacks must preserve their declared tensor/state contracts. Autocast affects eligible operations, not every tensor. CPU/MPS retain ordinary arithmetic. `"highest"` disables SNNLab CUDA autocast and selects highest matmul precision. |
| `fused_optimizer="auto"` | Applies when a custom factory returns an ordinary `torch.optim.Adam` or `AdamW` on CUDA, with fused/foreach unset. Arbitrary optimizers and subclasses are not automatically fused. Explicit optimizer options take precedence. |
| `dataset_prefetch=1` | Supports custom dataset encoders. An optional `device` keyword enables device-local encoding. Custom preparation runs on the caller thread under isolated RNG state, with bounded lookahead and CUDA transfer/encoding staging; it is not a background Python speedup. Encoders without device support prepare on CPU. |
| `projection_mode="fast"` | Optimizes eligible built-in zero-decay synapses. Custom synapses always execute their own equations. If a custom equation needs a zero-decay shortcut, its implementation must define that behavior deliberately. |

## Write the numerical update as a tensor function

Operate on the entire `(batch, cells)` tensor. The custom synapse receives an
already weight-projected drive; do not loop over edges or multiply weights again.
Keep state keys, shapes, devices and dtypes stable. Return new state tensors and
a new mapping, preserving auxiliary state with `{**context.state, ...}`.

Use broadcasting and `torch.where` for tensor-dependent decisions. A reset can
broadcast a scalar instead of constructing a full-sized constant tensor each
step. Both branches of `torch.where` evaluate, so keep both numerically valid.
Use `context.spike` to retain the configured surrogate gradient. Avoid detached
copies and reconstructing live tensors through `torch.tensor(...)`.

Validate configuration in `validate(config)` before stepping. Fixed scalar
calculations such as `math.exp(-context.dt_ms / context.config["tau_ms"])` can
specialize during compilation. Tensor data should remain on the device: avoid
`.item()`, `bool(tensor)`, `.tolist()`, `.cpu()`, NumPy conversions and Python
branches on tensor values inside updates. Logging, I/O and registry lookups also
belong outside numerical callbacks.

Under autocast, incoming matrix-product results may use BF16 while recurrent
state remains float32. The example synapse uses
`context.drive.to(context.state["value"].dtype)` before its recurrence; the neuron
similarly uses its voltage state's dtype for incoming currents. These casts
preserve the state contract. They do not undo rounding already introduced by an
upstream BF16 matrix product. Compare outputs, gradients and task accuracy with
`Performance(precision="highest")` when assessing precision changes.

## Declare capture safety explicitly

```python
from snnlab import extensions

extensions.register_neuron(
    "example.adaptive_lif/v1",
    "custom_neurons:adaptive_step",
    initialize="custom_neurons:adaptive_initial_state",
    validate="custom_neurons:validate_adaptive",
    input_unit="nA",
    state_units={"adaptation": "nA"},
    capture_safe=True,
)
extensions.register_synapse(
    "example.exponential_current/v1",
    "custom_neurons:exponential_step",
    initialize="custom_neurons:exponential_initial_state",
    validate="custom_neurons:validate_exponential",
    output_unit="nA",
    capture_safe=True,
)
```

This declaration is a contract, not a transformation or a safety checker.
The captured callbacks and state initializers must be deterministic tensor work
without random draws, host reads, Python side effects or external mutable state.
Python runs during warmup/capture; only recorded CUDA work repeats. A Python
counter, NumPy draw or external tensor mutation will not acquire normal per-call
behavior merely by adding the flag.

Training also requires capture-safe registered objectives, regularizers,
operations, surrogates and constraints used by the request. The optimizer
factory and random weight initialization run during setup, outside capture.
The example's clipped-normal weight initializer therefore retains its normal
seeded random draw without being marked capture-safe. A neuron or synapse's
state initializer can run inside a captured forward and must satisfy the flag's
contract.

Other eligibility rules still apply: compilation must be enabled, training
parameters must be float32, and tracing or strict extension value validation
prevents capture. Forward replay also falls back for autograd, runtime
continuation, recording, interventions, measurement windows and decision/reset
controls. Replay caches are bounded to two shapes. Structural validation retains
tensor shape/device/dtype/state-key checks; supported finite-value checks are
read after replay and still produce named errors.

## Validate correctness, then measure the intended workload

Start with strict extension validation, comparing eager and compiled execution
at the same precision. Check spikes, voltages, gradients and split-run
continuation; use appropriate floating-point tolerances. The example provides:

```sh
uv run python examples/customisation/customisation.py
uv run python examples/customisation/customisation.py --simulate --eager --extension-validation strict
uv run python examples/customisation/customisation.py --simulate --extension-validation strict
```

Structural validation is the default for normal execution. Once the callbacks
are validated, eligible repeated shapes can use replay. For example, with the
example's registered bundle and fixed stimulus already available:

```python
from snnlab.sim import Performance, build

built = build(
    graph=bundle.graph,
    device="cuda:0",
    performance=Performance(precision="highest"),
)
inputs = {"inputs": input_spikes.to("cuda:0")}
for _ in range(3):
    result = built.model(inputs, diagnostics=False)

print(result.metrics["cuda_graphs"])
print(result.metrics["execution_path"])
```

Here no parameters or inputs require gradients. Ordinary forward execution
selects `no_grad` for capture-safe custom components, and the third use of a
compatible shape can capture/replay. A build result describes preparation;
subsequent direct model results expose their own path/replay metrics. Public
`train` and `simulate` results consolidate them under
`result.metrics["performance"]`, separating requested settings, resolved policies
and actual paths. An automatic block target of 16 can coexist with an actual
kernel-loop block size of 1 and successful CUDA replay.

Repeated public `simulate` calls construct fresh models. Reuse a built
executor, or use dataset batching within one request, to amortize preparation
and reuse compatible shapes. Keep batch shapes stable where the workload
allows it; a tail batch can consume the second capture slot. Do not drop data
only to improve a timing result.

Measure the complete operation as well as warm execution, synchronizing the
accelerator for completed-work timings. Compilation, warmup and capture can
outweigh steady-state savings on small runs. The plotting example retains full
diagnostic histories and runs once on CPU by default, so it demonstrates callback
structure rather than a GPU speedup. Its `metrics.json` records the selected
paths and fallbacks; it does not imply that CUDA replay ran.
