---
title: Run Snapshots
description: Export the effective network, execution settings and optional parameter arrays.
---

Import `SnapshotSpec`, `RunSnapshot` and `write_run_snapshot` from `snnlab.sim`.
Use [`NetworkSnapshot`](/api/sim/experiment-utilities#networksnapshot) for structured,
metadata-only reading, units and explicit verified parameter loading.
Snapshots are optional inspection/provenance artifacts for `simulate` and
`train`. They capture the compiled
network and effective settings, rather than only the original request.

## Enable an export

```python
from snnlab import sim

result = sim.simulate(
    bundle="network.bundle",
    checkpoint="checkpoints/selected",
    input_bindings=(
        sim.PoissonInputBinding(
            input_id="inputs",
            steps_count=100,
            rates_hz=(20.0,),
            seed=17,
        ),
    ),
    snapshot="runs/example",
)
```

Replace `inputs` with the spike input declared by your network. The path shorthand
means `SnapshotSpec(path="runs/example", parameters=True, stage="start")`.
Omitting `snapshot` (the default `None`) disables capture and writing.
`build` requests reject snapshots: they do not execute or load weight checkpoints.

```python
sim.SnapshotSpec(
    path="runs/training",
    parameters=True,
    stage="both",
)
```

Use this value as a training request's `snapshot` argument to capture both initial
and final weights. `parameters=False` exports settings without copying or storing
parameter arrays. Snapshot capture is independent of `retain_parameters`.

## Capture stages and paths

1. `"start"` captures immediately before graph execution or training, after
   parameter initialization, checkpoint loading, input resolution and inference
   overrides. This is the default.
2. `"end"` captures the final model parameters after successful execution. In
   training these are the final weights, regardless of checkpoint selection.
3. `"both"` writes separate `start/` and `end/` directories below `path`.
   Single-stage exports write directly into `path`.

Training snapshots record `completed_updates`, including updates restored from a
resume checkpoint. A start snapshot can remain when execution fails; an end
snapshot is only written after execution succeeds. Existing snapshot files are
never overwritten: choose a fresh path for each run. Export I/O errors propagate
to the caller. Capture adds CPU transfers, array hashing, memory and disk costs;
leave it disabled for uninstrumented performance measurements.

## Files and contents

Each export contains `snapshot.json` and, when parameter arrays are included and
nonempty, `parameters.npz`. The JSON is published last. It contains:

1. Schema `snnlab.run-snapshot/v1`, SNNLab version, operation kind and stage.
2. The complete compiled `network`, preserving its native neuron/synapse fields,
   topology, units, initializers, constraints, extensions and modulation settings,
   plus its `graph_digest`.
3. The training recipe when training, and requested execution settings under
   `request`. The effective device, timestep, duration, seed and resolved input
   protocol are under `execution`, together with initialization metadata.
4. For inference, loaded checkpoint provenance, requested overrides and effective
   Poisson bindings. Overridden timestep values also appear in the exported graph;
   exported parameter arrays include projection scaling.
5. For training, effective batching, metric and selection policies, batch size
   and the number of completed updates.
6. A `parameters` inventory mapping original parameter names to NPZ keys, shapes,
   original dtypes and storage dtypes. `parameter_file_sha256` identifies the NPZ
   content. Parameter units and semantic dimensions remain in the compiled graph.

Input/target arrays are described by shape, dtype and SHA-256 of contiguous bytes;
array contents are not embedded. Source paths and binding metadata are retained
when supplied. Callable settings are described by their import names. Runtime
continuation records its compatibility signature and completed step count, not its dynamic state.

```python
import json
import numpy as np

with open("runs/example/snapshot.json") as stream:
    metadata = json.load(stream)

with np.load("runs/example/parameters.npz", allow_pickle=False) as arrays:
    weights = {
        name: arrays[row["key"]].copy()
        for name, row in metadata["parameters"].items()
    }
```

`bfloat16` parameters use `uint16` storage to preserve their exact bits; inspect
`dtype` and `storage_dtype` before interpreting those arrays. For example,
`torch.from_numpy(array).view(torch.bfloat16)` reconstructs them.

Snapshots describe a run; they do not package the dataset, extension code,
optimizer state, RNG state or dynamic neuron state. They are not a reload API or
a guarantee of identical results across environments. Use
[training checkpoints](/api/sim/training-checkpoints) and
[runtime state](/api/sim/runtime-state) for supported continuation.

## Re-export a captured snapshot

```python
snapshot = result.snapshots["start"]
sim.write_run_snapshot("runs/example-copy", snapshot)
```

`result.snapshots` maps captured stages to `RunSnapshot` objects. It is empty when
capture is disabled. Each object has JSON-compatible `metadata` and independent,
detached CPU `parameters`; subsequent model updates do not change the captured
arrays. The dictionaries/tensors remain user-editable. `write_run_snapshot(path,
snapshot) -> Path` writes these captured values without rebuilding or re-running
the model. It regenerates the parameter inventory and NPZ digest at export time.
