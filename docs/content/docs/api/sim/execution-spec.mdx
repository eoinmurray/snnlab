title: ExecutionSpec
description: Complete reference for configuring graph construction, simulation, inference and training.

`ExecutionSpec` describes one execution request. It selects the graph, input data, device, diagnostics and optional training or inference settings. Creating the object does not run anything; pass it to `build`, `simulate`, `infer`, `train` or `execute_request`.

Import it from `snnlab.sim`. This reference describes the current request contract in [requests/spec.py](https://github.com/eoinmurray/snnlab/blob/main/src/snnlab/sim/requests/spec.py). The [quickstart](/quickstart) demonstrates its simulation use.

## Constructor

```python
from snnlab.sim import ExecutionSpec

ExecutionSpec(
    kind: Literal["build", "simulate", "train", "infer"],
    snapshot: str | Path | SnapshotSpec | None = None,
    executor: Literal["graph"] = "graph",
    bundle: Path | None = None,
    graph: Mapping[str, Any] | None = None,
    input_bindings: Sequence[InputBinding] = (),
    protocol: Mapping[str, Any] = {},
    training: Mapping[str, Any] | None = None,
    targets: Mapping[str, torch.Tensor] = {},
    target_bindings: Sequence[TargetArrayBinding] = (),
    validation: ValidationSpec | None = None,
    epochs: int = 0,
    batch_size: int | None = None,
    shuffle: bool = False,
    batching: Batching | None = None,
    metrics: TrainingMetrics | None = None,
    on_epoch_end: Callable[[EpochReport], None] | None = None,
    updates: int | None = None,
    save_final_checkpoint: str | Path | None = None,
    save_selected_checkpoint: str | Path | None = None,
    seed: int = 0,
    device: str = "auto",
    diagnostics: bool = True,
    checkpoint: Path | None = None,
    runtime_state: GraphRuntimeState | None = None,
    options: Mapping[str, Any] = {},
    observations: EpochObservations | None = None,
    checkpoint_selection: CheckpointSelection | None = None,
    interventions: Sequence[Intervention] = (),
    resets: Sequence[ResetVoltage] = (),
    decisions: DecisionSegments | None = None,
    measurement: MeasurementWindow | None = None,
    recording: RecordingSpec | None = None,
    retain_outputs: bool = True,
    retain_parameters: bool = True,
    retain_final_state: bool = True,
    retain_runtime_state: bool = True,
    projection_mode: Literal["fast", "strict"] = "fast",
    extension_validation: Literal["strict", "structural"] = "structural",
    compile_mode: Literal["default"] | None = None,
    dataset_prefetch: int = 0,
    timing_mode: Literal["synchronized", "enqueue"] = "synchronized",
    training_timing: bool = False,
    tracing: TraceSpec | None = None,
)
```

This is a signature display, not executable construction code. `Path`, `Mapping`, `Sequence`, `Literal`, `Any` and `torch.Tensor` denote Python types. Empty mappings and sequences are created by dataclass factories for each instance; the displayed `{}` defaults are not shared mutable defaults.

The class is a frozen dataclass. You cannot reassign its fields, but nested mappings, tensors and objects are not deeply frozen. Construction validates execution-control enums, boolean retention/timing flags, recording/measurement types and supported tracing use. Handlers and input resolvers perform additional graph-dependent checks described below.

## Request and graph

### kind

**Type:** `Literal["build", "simulate", "train", "infer"]`. **Required.**

Chooses the handler when using `execute_request(spec)`:

| Value | Operation |
| --- | --- |
| `"build"` | Validate/lower the graph and initialize a `GraphExecutor`. No input execution. |
| `"simulate"` | Build and execute the graph using resolved inputs. |
| `"infer"` | Currently delegates to the graph simulation handler, including checkpoint loading. |
| `"train"` | Build the graph and perform optimizer updates using a training recipe and targets. |

Calling a handler directly selects that operation independently of `kind`: `simulate(spec)` does not dispatch on `spec.kind`. Keep `kind` consistent with the handler. In particular, `build` only automatically loads bundle training metadata when `kind="train"`. An unsupported `kind` raises `ValueError` in the dispatcher.

### executor

**Type:** `Literal["graph"]`. **Default:** `"graph"`.

The Python API and CLI execute graphs. `ExecutionSpec` rejects every executor value except `"graph"` with `ValueError`. `execute_request(spec)` dispatches directly to the graph handler.

### bundle

**Type:** `Path | None`. **Default:** `None`.

Path to a compiled bundle directory containing the graph and its authenticated manifest. Use `Path("network.bundle")`. Loading verifies the bundle's digests, then automatically imports any referenced external extension modules. The bundle contains JSON implementation references and no Python source. Missing paths raise `FileNotFoundError("bundle not found: ...")`; unavailable callbacks and mismatched declared package versions fail explicitly.

For graph execution, supply `bundle` or `graph`. When `graph` is provided, it takes precedence for construction. If both are supplied, training can still read its recipe from `bundle`; prefer one graph source to avoid ambiguity.

With `kind="train"`, a bundle can supply its `training.json` recipe when the `training` field is absent.

### graph

**Type:** `Mapping[str, Any] | None`. **Default:** `None`.

A compiled graph mapping, commonly `bundle.graph` returned by `lang.compile`. Pass graph data, not an authoring `Network` or a `Bundle` object.

The planner validates topology and backend capabilities before stepping. Supported graph execution includes COBA-LIF, current-based LIF and leaky-integrator populations, AMPA/GABA/current/integrator projections, supported and registered custom readout operations, feedforward/recurrent/feedback paths and timestep-aligned delays. Unsupported structures raise capability or validation errors.

If neither `graph` nor `bundle` supplies graph data, graph execution raises `ValueError`.

## Inputs

### input_bindings

**Type:** `Sequence[InputBinding]`. **Default:** `()`.

Supplies all input data for the request. Pass typed binding instances in one sequence, for example `input_bindings=(poisson_input,)`. Binding IDs must match inputs declared by `net.input`.

Declare the accepted signal with [Network.input](/api/lang/network#input). The binding types and their compatibility rules are documented below. Import bindings and `InputBinding` from `snnlab.sim`.

### Binding rules

All graph inputs must be covered exactly once by name. Names refer to IDs declared by `net.input`, not population names. Input tensors resolve the symbolic time and batch axes; the graph supplies the timestep and feature/channel dimensions.

### InputBinding

[`ExecutionSpec.input_bindings`](/api/sim/execution-spec#input_bindings) is the sole input field on the execution request. `InputBinding` is a public type alias from `snnlab.sim`:

```python
InputBinding = (
    DenseArrayBinding
    | EventStreamBinding
    | PoissonInputBinding
    | DatasetSnapshotBinding
)
```

Pass instances of these types in one sequence; the executor routes each by its type. A one-binding tuple is `(binding,)`. Each binding's `input_id` must identify a declared graph input. Unknown binding types raise `TypeError`; duplicate input IDs raise `ValueError`, including duplicates across binding types.

Dense and event bindings may be combined for different graph inputs. Poisson bindings must be used without replay bindings. A dataset snapshot must be the only binding in the sequence; multiple snapshots are not currently supported. The public request has no separate `inputs`, `event_bindings`, `poisson_bindings` or `dataset_binding` arguments.

### DenseArrayBinding

Explicit dense tensors with source metadata. Each binding has `input_id: str`, `value: torch.Tensor` and `source: Mapping[str, Any]`, which defaults to an empty mapping.

Use this route when retaining file or dataset provenance matters. The `source` mapping records supplied metadata; constructing an in-memory binding does not authenticate an arbitrary file by itself. File-loading helpers can supply file digests.

Dense values normally use `(time, batch, *features)` axes. A missing batch axis can be inserted as a singleton. Feature dimensions must match the graph, and all inputs must share time/batch sizes. Spikes must be binary; masks must be boolean or zero/one; floating values must be finite. Non-mask values are converted to floating tensors on the selected device.

Place each dense binding in `input_bindings`, for example `input_bindings=(DenseArrayBinding("inputs", spike_tensor),)`. Dense and event bindings may coexist for different inputs when resolved timestep, duration and batch dimensions agree.

### EventStreamBinding

Sparse binary spike events. Each binding declares `input_id`, integer coordinate tensors `steps`, `batches`, `channels`, positive `steps_count`, positive `batch_size`, and optional `source` metadata.

Coordinates are zero-based simulation steps, batch indices and channel indices. Coordinates must satisfy the resolver's ordering and bounds checks; duplicates are rejected. The input must be a spike input with a time/batch/channel declaration. Resolution materializes binary dense spikes and retains event counts/provenance.

Place each event binding in `input_bindings`. Event bindings can accompany dense bindings for other graph inputs; they cannot accompany Poisson bindings or a dataset snapshot.

### PoissonInputBinding

Generates seeded spike inputs. Pass it as `input_bindings=(poisson_input,)`.

| Binding field | Type / default | Meaning |
| --- | --- | --- |
| `input_id` | `str`, required | Exact graph input ID. |
| `steps_count` | `int`, required | Positive number of simulation steps. |
| `batch_size` | `int = 1` | Positive number of presentations. |
| `rates_hz` | `Sequence[float]`, required | Finite, non-negative rates in spikes per second. |
| `seed` | `int`, required | Seed of this binding's CPU random generator. |
| `categorical` | `bool = False` | If true, select one listed rate uniformly and independently per presentation. |

The input declaration must have `(time, batch, channels)` axes and spike signal type. With `categorical=False`, exactly one rate is required and applies to all channels/presentations. With `categorical=True`, one selected rate applies to all channels of each presentation; spike samples are independent across channel/time positions.

Generation uses a Bernoulli discretization of a homogeneous Poisson process. The per-step probability is the selected rate in Hz multiplied by the graph timestep in milliseconds and divided by 1,000. A probability above one is rejected. Configured and selected rates, seeds and resolved shapes are retained in the execution protocol.

Multiple Poisson bindings must agree on time and batch sizes and cover all graph inputs. Poisson inputs cannot currently be mixed with dense/event replay or a dataset snapshot.

### DatasetSnapshotBinding

Binds one immutable external NPZ dataset snapshot. Graph execution automatically uses a batch provider; no lazy/batchwise flag is required. Pass it as `input_bindings=(dataset_input,)`. Its fields are:

| Field | Type / default |
| --- | --- |
| `path` | `Path`, required |
| `input_id` | `str`, required |
| `dataset_id` | `str`, required |
| `split` | `str`, required |
| `encoder` | `DatasetEncoder`, required |
| `target_id` | `str | None = None` |
| `feature_key` | `str = "features"` |
| `label_key` | `str = "labels"` |
| `sample_cap` | `int | None = None` |
| `shuffle` | `bool = False` |
| `order_seed` | `int = 0` |

The resolver computes the source file digest, selects samples with the cap/order settings, and records file identity, split, selected indices, encoder and seeds. It performs no dataset download or registry lookup. `dataset_id` and `split` must be non-empty.

`DatasetEncoder` has required `kind`, optional `duration_ms`, `max_rate_hz` and `rates_hz` (all default `None`), and `seed=0`. The `"custom"` kind uses a registered encoder with `definition` and `config`; see [Extensions](/api/lang/extensions#dataset-encoders-and-inputs). Built-in kinds are `"rate_poisson"` for normalized sample/channel features, `"prebinned_spikes"` for binary time/sample/channel tensors, and `"event_bin"` for timestamped sample/channel events. Encoding validates shapes, values and physical timing against graph `dt`.

A dataset snapshot must be the only element of `input_bindings`. During training it is also exclusive with explicit targets/target bindings; use its `target_id` to bind integer labels to the recipe's target. Simulation resolves the input and does not use its labels as training targets.


### Automatic batch encoding

Dataset bindings resolve content identity, sample selection, labels and ordering without constructing the whole time-by-sample spike tensor. The provider verifies source-file stability while extracting arrays once into private temporary NPY files, then uses read-only memory mappings. Built-in encoders produce only the current batch on CPU and transfer it to the execution device; custom encoders retain their registered backend/configuration. Temporary mappings live with the provider; they are not a dataset registry. Dataset download and split construction remain caller responsibilities.

`ExecutionSpec.batch_size` controls the encoded batch size. When omitted for a dataset binding, the default is 32, bounded by sample count. Snapshot training with `epochs=0` automatically runs one epoch; positive epochs and `updates` retain the normal schedule/truncation semantics, including a smaller tail batch. Dense/event/Poisson input bindings retain their existing direct replay/full-batch interfaces.

For `rate_poisson`, features must have `(samples, channels)` shape and floating values in `[0, 1]`. Specify a positive timestep-aligned `duration_ms` and **either** `max_rate_hz` for a fixed feature-scaled rate **or** `rates_hz` for categorical rates:

```python
encoder = DatasetEncoder(
    "rate_poisson",
    duration_ms=200,
    rates_hz=(40, 80, 120),
    seed=17,
)
```

Categorical selection is uniform and independent per presentation: one maximum-pixel rate is selected for each sample and scales its feature values throughout that presentation. Rates must be finite, non-negative and satisfy `rate_hz * dt_ms / 1000 <= 1`. Rate-selection and Bernoulli spike-generation streams are separate, so selecting rates does not consume the spike stream. Training re-encodes each batch with fresh draws at each epoch. Training-split evaluation, validation and named observation probes use fixed separate phase streams; evaluating or adding probes cannot change subsequent training draws.

`prebinned_spikes` and `event_bin` preserve exact supplied spikes with no stochastic re-encoding. Sparse events are binned only for selected samples; unlisted bins are zero. Custom registered encoders receive the same read-only arrays and callback signature as before, but `selected` identifies only the current batch and `seed` is a derived batch/draw seed. Custom callbacks must preserve presentation duration and must not mutate the snapshot or retain full-dataset encoded tensors. Their global Python/NumPy/Torch randomness is scoped to that seed without perturbing model RNG streams.

`result.metrics["execution_protocol"]["batch_encoding"]` uses `snnlab.batch-encoding/v1` and records the encoder backend (CPU for built-ins), fresh-training/fixed-evaluation policy, selected draw seeds and separate ordering/rate/spike stream roots. Derived rate/spike seeds bind phase, epoch, ordered absolute sample indices and draw seed. Epoch order remains `execution_seed + epoch`. Per-update `encoding` metadata records coordinates, stream seeds and selected categorical rates. Input memory scales with presentation steps, batch size and channels; retained outputs and requested diagnostics can still grow with dataset size.

Checkpoints retain this versioned encoding protocol with epoch/next-batch coordinates and model/optimizer/RNG state. Coordinate-derived streams regenerate the next batch exactly on resume. Changed source contents, encoder settings, seeds, sample selection or batch schedule are rejected. Earlier checkpoints with eagerly encoded/reused dataset spikes cannot silently resume under the new protocol. Exact dense/event input bindings remain available for explicitly retained replay.

Dataset simulation/inference also encodes successive batches using one model/checkpoint load and fixed inference draws, concatenating outputs along the sample axis. `encoding_batches` records each encoded batch. Separate batches start with fresh dynamic neuron state. Multiple-batch results have `runtime_state=None`; dataset runtime continuation requires a single complete batch. Full-batch dense/sparse replay interventions are authenticated before execution and sliced along the selected sample axis for each batch.

The low-level `resolve_dataset_snapshot_binding` helper remains an explicit eager materializer for callers needing a complete dense replay. Normal request/CLI execution automatically chooses the provider.


### protocol

**Type:** `Mapping[str, Any]`. **Default:** empty mapping.

Additional JSON-serializable execution provenance. For example, a `dataset` mapping can identify the source and split. It is metadata, not a way to change the graph or generate inputs.

Resolvers own reserved fields such as `schema`, `binding_schema`, `representation`, `inputs`, `timing` and `seeds`; attempting to override them raises `ValueError`. Dense/event resolvers also reserve `masks`; the dataset resolver reserves its additional dataset/snapshot/resolution fields. Use descriptive custom keys instead of resolver-owned fields. The finalized protocol appears in `result.metrics["execution_protocol"]`.

## Training

Custom training callbacks are documented in [Extensions](/api/lang/extensions#objectives-and-regularizers). Classification targets are integer labels; custom regression targets can be finite real tensors with a leading sample axis.

### training

**Type:** `Mapping[str, Any] | None`. **Default:** `None`.

A compiled training recipe, typically `bundle.training`, rather than an authoring `TrainSpec` instance. It describes objectives, parameter groups, optimizer, surrogate gradients and regularizers. When omitted, a training bundle can supply the recipe.

Graph training requires a recipe with resolved trainable parameters and external targets. The trainer supports cross entropy, spike budgets and AdamW, plus registered custom objectives, regularizers, optimizers and surrogates. Unsupported recipes, missing trainable parameters or unsupported optimizers fail. Direct training fields control iteration as described below; the recipe's epoch count is not automatically used by direct `train(spec)`.

`build` uses recipe trainable parameter IDs and surrogate slope when present. For a normal simulation request, training objectives and targets are not evaluated.

### targets

**Type:** `Mapping[str, torch.Tensor]`. **Default:** empty mapping.

Named training target tensors. Keys must match the objective target IDs exactly, with one leading entry per input sample/batch-axis element. Classification objectives require one-dimensional labels using `int8`, `int16`, `int32`, `int64` or `uint8`; resolved labels become `torch.long`, and objective evaluation checks valid classes. Custom non-classification objectives accept finite real tensors, including multidimensional regression targets, and preserve their dtype.

Supply `targets` or `target_bindings`, not both. Dataset snapshot labels use the snapshot's `target_id` instead. Simulation/inference do not consume these training targets.

### target_bindings

**Type:** `Sequence[TargetArrayBinding]`. **Default:** `()`.

Explicit target vectors with provenance. Each binding has required `target_id: str` and `value: torch.Tensor`, plus `source: Mapping[str, Any] = {}` from a dataclass factory. IDs, shape and integer-value rules match `targets`. Duplicate/missing/unexpected target IDs are rejected.

### training_timing

**Type:** `bool`. **Default:** `False`. Requires `kind="train"`.

Set `training_timing=True` to return `result.metrics["training_timing"]`. The CLI
provides `--training-timing`. Timing does not change the recipe, data order, loss,
checkpoint identity or resume protocol. The metric is absent when disabled, and
no timing clocks or timing fences are used.

```python
execution = ExecutionSpec(
    kind="train",
    bundle=bundle_path,
    input_bindings=(train_input,),
    targets={"class": train_labels},
    validation=validation,
    epochs=20,
    batch_size=32,
    shuffle=True,
    training_timing=True,
)
result = train(execution)
timing = result.metrics["training_timing"]
print(timing["total_s"], timing["training_s"])
for row in timing["epochs"]:
    print(row["epoch"], row["training_s"], row["validation_s"])
```

The mapping has `mode`, `scope`, `training_scope`, `total_s`, the phase fields
below, and `epochs`. All durations are seconds. Phase totals are disjoint and sum
to `total_s`.

| Field | Scope |
| --- | --- |
| `setup_s` | Model construction, input/target resolution, optimizer/resume setup and scheduling before initial evaluation. |
| `training_s` | Minibatch preparation, forward/loss/backward, optimizer updates, constraints, update bookkeeping and in-loop batch-loss checkpoint selection. Excludes epoch evaluations. |
| `train_evaluation_s` | Fixed-weight training-split evaluations, including epoch 0 when evaluated. |
| `validation_s` | Held-out evaluations and optional named observation probes. |
| `checkpoint_s` | Final checkpoint construction and any requested `save_final_checkpoint` / `save_selected_checkpoint` writes. |
| `reporting_s` | Epoch metric/observation bookkeeping, epoch-selection checkpoints and final result construction outside the other phases. |

`epochs` contains phase durations for epochs evaluated or trained during this
call. Epoch 0 has evaluation time and zero training time. Completed-epoch rows
are numbered from 1. A resumed partial epoch reports only work performed in the
current call; timings are not accumulated from its checkpoint. Single-batch
`updates` mode has an empty epoch timing list and still reports phase totals.
Initial evaluation can be skipped on mid-epoch resume. Truncated calls can have a
training timing row for a partial epoch without a completed-epoch evaluation.

With `timing_mode="synchronized"` (default), CPU wall clocks and CUDA/MPS device
fences bracket phase/epoch transitions. There are no per-forward/backward timing
fences. Opt-in `"enqueue"` omits timing fences and records host elapsed time;
queued GPU work can extend beyond a phase, so those values cannot establish
completed GPU speedups. Fences can change overlap and add overhead; disclose the
measurement mode when comparing throughput.

`total_s` starts after request validation and an initial device fence, and ends
after in-memory result construction and a final device fence. Caller-side data
preparation, warmup, plotting and external checkpoint/volume writes are excluded.
Put those operations outside both comparison timers and use identical initial
and completed-epoch evaluation schedules. Isolated forward/backward latencies
require a separate profiler; `training_s` is not their sum alone.

### validation

**Type:** `ValidationSpec | None`. **Default:** `None`.

Held-out data for epoch evaluation by `train`. Import `ValidationSpec` from `snnlab.sim`:

```python
validation = ValidationSpec(
    input_bindings=(validation_input,),
    targets={"class": validation_labels},
)
execution = ExecutionSpec(
    kind="train",
    bundle=bundle_path,
    input_bindings=(train_input,),
    targets={"class": train_labels},
    validation=validation,
    epochs=20,
    batch_size=32,
    shuffle=True,
)
result = train(execution)
history = result.metrics["epochs"]
```

`ValidationSpec` is a frozen dataclass with `input_bindings: Sequence[InputBinding] = ()`, `targets: Mapping[str, torch.Tensor] = {}`, `target_bindings: Sequence[TargetArrayBinding] = ()`, `protocol: Mapping[str, Any] = {}`, and `encoding_seeds: Sequence[int] = ()`. Defaults use independent factories. It uses the same [input binding rules](/api/sim/execution-spec#input_bindings) and target validation as training, including dataset snapshots with a `target_id`. Supply `targets` or `target_bindings`, not both; snapshot labels must not be combined with either.

Validation uses the same graph, current parameters, execution seed and device. It does not update parameters or optimizer state, retains no diagnostic traces, and runs without gradients. Its resolved provenance appears separately in `result.metrics["validation_protocol"]`; it does not change the training checkpoint's execution protocol. Validation data can be changed on resume when observations, retained reporting policies and epoch checkpoint selection are disabled. Audits require the same validation identity; epoch selection also verifies the resolved evaluation inputs and labels by content digest.

For stochastic dataset validation, `encoding_seeds=(101, 103)` requests explicit repeatable draw sets; omission uses the encoder seed for one fixed draw. Each draw evaluates all selected samples in bounded batches, and loss/components/accuracies are sample-weighted across all draws. Epoch rows report `validation_encoding_draws`; observations count each draw's presentations. Encoding seeds require a stochastic dataset encoder, must be distinct non-negative integers, and are bound into validation/selection/audit identity.

This field is used only by graph `train`, and requires positive effective `epochs`. Other handlers do not evaluate validation data. See [epoch metrics](#epoch-metrics) and the [Training example](/training).

### observations

**Type:** `EpochObservations | None`. **Default:** `None`. Requires graph `train` with positive `epochs`.

Import `EpochObservations` and `ObservationProbe` from `snnlab.sim`. Select exact graph IDs; all selections default to empty tuples and `probes` to an independent empty mapping. Unknown IDs, duplicate IDs, non-spiking population selections and non-trainable gradient selections are rejected.

```python
observations = EpochObservations(
    population_rates=("cell_E", "cell_I"),
    parameter_norms=("cell_E_to_I.weight", "w_out"),
    output_activity=("output_neurons",),
    gradient_norms=("w_out",),
    probes={
        "reference": ObservationProbe(input_bindings=reference_inputs, seed=17),
        "validation_draw_1": ObservationProbe(
            input_bindings=draw_inputs,
            seed=23,
            split="validation",
        ),
    },
)
execution = ExecutionSpec(
    kind="train",
    graph=bundle.graph,
    training=bundle.training,
    input_bindings=train_inputs,
    targets=train_targets,
    validation=validation,
    observations=observations,
    epochs=20,
    batch_size=32,
    diagnostics=False,
)
```

| Selection | Meaning |
| --- | --- |
| `population_rates` | Population IDs for mean firing rates in Hz. |
| `parameter_norms` | Parameter IDs for the L2 norm of each flattened stored tensor. |
| `output_activity` | Spiking population IDs for per-cell spike totals, silence and shares. A non-spiking MeanVoltage integrator is not a spike-output population. |
| `gradient_norms` | Trainable parameter IDs for epoch-average gradient norms before/after clipping. |
| `probes` | Named `ObservationProbe` draws, measured independently from training and ordinary validation. |

`ObservationProbe(input_bindings=(), seed=0, split="reference", protocol={})` accepts the standard input binding types, a nonnegative integer evaluation seed, and split `"reference"` or `"validation"`. Probes measure activity only; they have no targets, loss or accuracy and never participate in optimization. Dataset snapshot labels are ignored for activity-only probes. Each resolved draw and its protocol are retained under its own name; multiple validation draws remain separate rather than being silently pooled. Poisson/dataset encoders retain their binding-specific seeds; the probe seed controls the fallback resolution/evaluation stream. Dense/event/ordinary Poisson draws are resolved once and reused for fixed-weight evaluation. Dataset probes regenerate their same deterministic draw in bounded batches; training draws use a separate fresh stream.

Observations run at initialization and completed epoch boundaries. Evaluation uses fresh dynamic state, fixed current weights and `batch_size`, with compact per-batch spike counts rather than additional dense spike histories. Declared graph outputs and loss regularizers may still require histories. The feature does not claim constant-memory training or redesign input encoding. Python, NumPy, PyTorch CPU and available accelerator RNG states are restored around evaluations, including on errors; extra probes do not change training randomness or optimizer updates.

Audited checkpoints use checkpoint schema version 3, which requires this feature's reader; ordinary checkpoints continue to use version 2. Audited checkpoints retain completed history and partial-epoch gradient totals. Resume requires the same observation configuration, validation identity, draw identities, evaluation seed and batch size. A checkpoint without observation history cannot retroactively start an audit: missing measurements are not reconstructed. Ordinary checkpoints without observations retain their existing resume behavior. See [Epoch observations](/api/sim/execution-result#epoch-observations) for result fields and aggregation.

### Training controls

These are direct `ExecutionSpec` constructor fields, used by graph `train`:

| Field | Type and default | Behaviour |
| --- | --- | --- |
| `epochs` | `int = 0` | A positive integer enables dataset iteration across the input sample axis. `0` selects repeated full-batch updates. |
| `batch_size` | `int \| None = None` | Positive minibatch size in dataset mode; `None` uses all supplied samples. No remainder batch is dropped. |
| `shuffle` | `bool = False` | In dataset mode, permute sample order each epoch with `seed + epoch`. |
| `updates` | `int \| None = None` | Optional positive update limit for this invocation. `None` runs the remaining epoch schedule, or one update in full-batch mode. |
| `save_final_checkpoint` | `str \| Path \| None = None` | Write the final checkpoint to this directory when supplied. |
| `save_selected_checkpoint` | `str \| Path \| None = None` | Write the winning checkpoint under `checkpoint_selection`. Fails if no eligible candidate exists. |

`epochs` must be a non-negative integer; supplied `batch_size` and `updates` must be positive integers. Boolean or fractional values are rejected for these counts, and `shuffle` must be boolean. Without dataset mode, `batch_size` and `shuffle` do not split or shuffle the repeated full batch. A dataset checkpoint already at its requested end epoch raises an error.

A resumed dataset schedule starts at the checkpoint's next coordinates and is truncated by `updates` when supplied. The training recipe's `epochs` does not override this execution field. These controls do not change graph simulation or inference.

Dataset bindings automatically use one epoch when `epochs=0` and a maximum default batch size of 32 when `batch_size=None`.

The previous training keys in `options` are no longer accepted by graph `train`; move them to the constructor fields. Inference-specific mappings remain under `options`.

### metrics

Import `TrainingMetrics` from `snnlab.sim`. This execution policy changes measurement, independently of the scientific objective in `TrainSpec`. Omitting it uses online training metrics, validation evaluation at initialization and every completed epoch, and no update history.

```python
metrics = TrainingMetrics(
    train="online",
    validation="epoch",
    initial=("validation",),
    update_history=False,
)
```

| Field | Values and semantics |
| --- | --- |
| `train` | `"evaluate"`: full training split at fixed current weights. `"online"` (default): reuse each pre-update minibatch's scores. `"none"`: no training metrics. |
| `validation` | `"epoch"` (default): evaluate supplied held-out data after each completed epoch. `"none"`: no validation evaluation. |
| `initial` | Unique split names; default `("validation",)`. Requesting initial train requires `train="evaluate"`; requesting initial validation requires `validation="epoch"`. An absent ValidationSpec produces absent validation metrics. |
| `update_history` | Boolean, default `False`. `False` returns an empty update history and omits per-update loss/component retention. |

Online metrics accumulate detached objective/regularizer loss sums, unweighted classification cross-entropy sums and correct counts on-device. They transfer at completed epochs or explicitly saved checkpoint boundaries, without another training forward or retained autograd graph. Loss is the example-weighted mean of minibatch mean objectives (including objective weights and regularizers). For custom classification losses this is the custom objective's minibatch aggregation, which may differ from a full-dataset class-normalized objective. Reported cross-entropy always uses ordinary unweighted per-example CE, separately from that custom objective. Accuracy weights actual examples, including unequal tails.

Initial online training metrics are absent. Rows label online results `train_measurement="online_pre_update"` and evaluated results `*_measurement="fixed_weight_evaluation"`, with presentation counts in `*_examples`. Online values describe changing weights throughout an epoch.

`update_history=False` also disables **implicit** historical update-loss checkpoint selection. Set an explicit validation `CheckpointSelection()` to retain a winner without update loss reads, or explicitly request `CheckpointSelection.legacy_training_batch_loss()` to preserve update selection and its host scalar decisions. `CheckpointSelection.disabled()` disables selection independently of history. Saving a selected checkpoint requires an enabled selection policy. Selection by epoch metrics requires fixed-weight evaluation of its split; online train metrics cannot silently stand in for evaluated train metrics. `include_initial=True` also requires that initial split measurement. Split activity observations require their normal evaluations; parameter/gradient observations and separately declared probes remain available.

Default online metrics, explicit metrics, batching or callbacks retain contiguous available epoch history and partial online sums in authenticated training checkpoint schema version 5. Resume requires the same measurement policy and protocol identities, restores partial sums and next coordinates, and emits only newly completed epochs. Online metrics and explicit metric or batching policies additionally bind input/target contents; callback-only reporting uses existing protocol metadata without transferring input tensors. Older checkpoint versions still load under their original contracts. Changing measurement or schedule policy rejects resume.

### batching

Import `Batching` from `snnlab.sim`. Omitting it preserves the existing `shuffle` flag and kept tail.

```python
batching = Batching(
    order="stratified",
    stratify_by="class",
    remainder="merge_small",
    min_batch_size=20,
)
```

`order` is `"sequential"`, `"shuffle"` or `"stratified"`. Sequential preserves input order; shuffle retains the historical CPU `randperm` path. Stratification requires a named training target with one nonnegative integer label per example. Only represented labels form queues; missing classes and scarce classes never create samples. Each sorted class queue is shuffled with a private CPU generator seeded by `ExecutionSpec.seed + zero_based_epoch`. Its examples get fractional positions `(j + 0.5) / class_count`, where `j` is the zero-based queue index. Queues merge by increasing position; a seeded permutation supplies random tie order before stable sorting. The generator is separate from training/encoding RNG streams. Natural unequal class counts remain unchanged; no validation labels are used.

With explicit batching, `shuffle=False` is neutral; `shuffle=True` is allowed only with `order="shuffle"`. Contradictory settings raise an error. `stratify_by` requires stratified order.

| Remainder | Coverage |
| --- | --- |
| `"keep"` (default) | Retain every example once, including a smaller final batch. |
| `"drop"` | Explicitly omit the short final batch; fail if that would drop the entire dataset. |
| `"merge_small"` | Merge a tail strictly smaller than `min_batch_size` into the preceding batch. With no preceding batch, keep the small dataset. |

`min_batch_size` is required only for `merge_small`, and must be a positive integer no larger than `batch_size`. It is a tail threshold, not a class quota. For 200 examples, batch size 64 and threshold 20, batch sizes are 64/64/72. A merged final batch may exceed the nominal size. The policy does not impose any objective weighting.

Resolved schedule metadata lives at `result.metrics["execution_protocol"]["training_iteration"]["batching"]`, including algorithm, label digest, actual batch sizes, examples/batches per epoch and dropped examples. Epoch rows record actual `epoch_examples`, `epoch_updates`, `dropped_examples`, cumulative `examples` and absolute `update`. Encoding requests use the actual ordered indices and batch sizes. Checkpoint coordinates, update limits and epoch boundaries use the resolved schedule.

### on_epoch_end

Optional callable receiving an immutable `EpochReport`, once after each **newly completed** epoch's requested measurements and observations. Epoch-zero evaluation remains in history and does not invoke the hook. The hook receives no model or optimizer references; merely enabling it adds no evaluations or unrequested observations.

```python
from snnlab.sim import EpochReport


def report_epoch(report: EpochReport) -> None:
    print(
        report.epoch,
        report.total_epochs,
        report.train.accuracy,
        report.validation.accuracy,
        flush=True,
    )
```

`report.epoch`, `total_epochs`, `updates` and `examples` are global counters. `train`, `validation`, `observations` and `timing` are recursively immutable host mappings supporting both key and attribute access. Unavailable split metrics, observations or disabled timing are `None`. Split values equal the corresponding retained epoch row. Python, NumPy, CPU and available accelerator RNG states are preserved around the callback, including on failure. Exceptions propagate; optimizer updates are not automatically retried.

With `training_timing=True`, `report.timing` contains wall seconds, `mode` and `total_s` through the report snapshot. It uses the configured synchronized/enqueue interpretation. It excludes the callback's own duration; the complete call's existing `reporting_s` includes callback overhead. After mid-epoch resume, timing describes work in this invocation, while metric sums and counters cover the full epoch. No guaranteed ETA is calculated. See the [runnable native example](/training#online-metrics-stratified-batches-and-progress).

## Randomness and device

### seed

**Type:** `int`. **Default:** `0`.

Execution seed used for graph parameter initialization and provenance. Training's shuffled epoch ordering uses `seed + epoch`. Interventions default to this seed when their own seed is absent.

Poisson bindings have their own explicit seeds. Dataset bindings separately declare `order_seed`, and rate encoders have an encoder seed. Setting `ExecutionSpec.seed` does not replace these independently configured seeds. A fixed seed supports repeatable runs under the same execution conditions; cross-device numerical equality is a separate question.

### device

**Type:** `str`. **Default:** `"auto"`.

Accepted values are `"auto"`, `"cpu"`, `"cuda"`, `"cuda:N"` and `"mps"` (normalized to lowercase by the resolver). Explicit unavailable CUDA/MPS requests raise `ValueError`; indexed CUDA availability/topology is additionally constrained by PyTorch.

`"auto"` first honors the `PINGLAB_DEVICE` environment variable. Otherwise it selects CUDA when available, then CPU. It does not automatically select MPS. Use `"cpu"` for the portable Quickstart behaviour.

## Diagnostics

### diagnostics

**Type:** `bool`. **Default:** `True`.

Declared outputs from `net.output` are always returned in `result.outputs`. Signals declared with `net.expose` are returned by default in `result.diagnostics`, keyed by their exposed names. Set `diagnostics=False` to return no diagnostic tensors. This applies to simulation, inference and training; `build` does not execute the network.

```python
net.output("spikes", cells.spikes)
net.expose(cells.voltage, name="e_voltage")
bundle = lang.compile(net, target="tools/snnsim")

execution = ExecutionSpec(
    kind="simulate", graph=bundle.graph, input_bindings=(poisson_input,)
)
result = simulate(execution)
spikes = result.outputs["spikes"]
voltages = result.diagnostics["e_voltage"]
```

Compile the network after declaring its outputs and exposed diagnostics. To disable diagnostics for a run, pass `diagnostics=False` to `ExecutionSpec`; outputs, training objectives/regularizers and continuation state are unaffected. The runtime requires a boolean value.

For leaky integrators, expose `.voltage` for post-reset membrane diagnostics or `.pre_reset_voltage` for pre-reset integration samples. See [Voltage sampling](/api/lang/operations-readouts#voltage-sampling) for reductions and older-graph compatibility.

Expose exactly the signals you want to inspect. Population spikes and voltages typically have `(time, batch, cells)` axes. Projection conductance is also explicitly exposable using `net.expose(projection.conductance, name="input_conductance")`, where `projection` is returned by `net.connect`. Exposed diagnostics are detached tensors; declared outputs retain their computation graph for training.

There is no automatic collection of unexposed signals. The previous `recording` and `recording_fields` constructor arguments have been removed, and `ExecutionResult.recordings` has been renamed to `diagnostics`. Training returns exposed diagnostics from its final update.

## Checkpoints and continuation

### checkpoint_selection

Import `CheckpointSelection` and `SelectionMetric` from `snnlab.sim`. Selection is an execution control, independent of `TrainSpec` and epoch observations:

```python
checkpoint_selection = CheckpointSelection(
    split="validation",
    cadence="completed_epoch",
    metric=SelectionMetric("cross_entropy", objective=0, direction="min"),
    tie_break=(SelectionMetric("accuracy", objective=0, direction="max"),),
    include_initial=False,
)
```

Pass this object as `ExecutionSpec.checkpoint_selection`. `split` is `"train"` or `"validation"`; validation selection requires `ValidationSpec`. Epoch selection requires positive `epochs`. `objective` is the zero-based training objective index and must identify a classification objective (built-in cross entropy or a custom objective registered with `classification=True`). Both metrics are measured from that objective's predictions; cross-entropy is **unweighted**, excludes regularizers, and is reported in epoch `*_cross_entropies` mappings. Metrics are sample-weighted across the entire resolved split, with a fixed evaluation seed and minibatch size.

`direction` supports `"min"` and `"max"`. Tie-break metrics are checked in declared order after an exact primary-score tie. An exact tie across all metrics retains the earliest candidate. Duplicate metrics, unknown indices, incompatible objectives, missing scores and non-finite scores fail explicitly. Only `cadence="completed_epoch"` is supported. The saved parameters, optimizer/RNG state and epoch coordinates belong to the weights actually evaluated.

`include_initial=False` excludes epoch 0. Setting it to `True` admits the initial state, including a zero-update winner. An update limit that ends before any eligible boundary returns `selected_checkpoint=None`; requesting `save_selected_checkpoint` then fails. There is no partial-epoch selection or early stopping.

Omitting the field preserves historical behavior, explicitly named `CheckpointSelection.legacy_training_batch_loss()`: lowest weighted pre-update training-batch loss selects post-update weights. This compatibility policy retains the historical metric/weight timing mismatch. Epoch selection corrects it for opt-in requests.

`CheckpointSelection.to_dict()` / `.from_dict()` round-trip the policy as JSON-compatible data. The resolved policy and evaluation contract are stored in checkpoint metadata, alongside the winning record and a separate best-candidate snapshot. Final checkpoints retain that winner across resume, including invocations without improvement. Selected checkpoints can themselves resume. Resume rejects changes to policy, evaluation seed/batch size, protocol, or resolved input/label contents. A checkpoint from before selection metadata existed cannot start epoch selection retrospectively; legacy resume retains its historical invocation-local baseline.

Epoch-selection checkpoints use schema version 4 (or version 5 when reporting state is retained) and require a compatible reader. Default legacy checkpoints keep schema version 2 (3 with observations), with additional selection metadata readable by this implementation. See [Checkpoint selection results](/api/sim/execution-result#checkpoint-selection) and [CLI](/api/sim/cli#checkpoint-selection).

### checkpoint

**Type:** `Path | None`. **Default:** `None`.

Weights or training state to load before execution. Behaviour depends on the handler:

| Handler | Behaviour |
| --- | --- |
| `simulate` / `infer` | A directory loads a digest-verified graph training checkpoint's parameters. A non-directory path loads a PyTorch state dictionary with `weights_only=True`; the keys must match `GraphExecutor.state_dict()`. Historical COBANet dictionaries require an application-owned conversion before loading. |
| `train` | Loads a graph training-checkpoint directory and resumes parameters, AdamW state, RNG state and iteration coordinates. |
| `build` | Does not load the checkpoint field. |

Inference authenticates the graph identity and parameter names/shapes/dtypes. It does not restore the training optimizer or training iterator. Inference metrics retain checkpoint provenance.

Training resume additionally checks recipe digest, resolved execution protocol, initializer metadata, parameter coverage, and compatible RNG backend/device topology before restoring state. In dataset iteration mode, next epoch/batch coordinates must be valid. Mismatches raise errors rather than silently starting a different trajectory.

### runtime_state

**Type:** `GraphRuntimeState | None`. **Default:** `None`.

Dynamic state for continuing a simulation trajectory. Obtain it from `result.runtime_state`; it contains compatibility/signature information, completed steps, voltages, refractory counters, conductances, population delay histories and input delay histories. Static weights are excluded.

This is distinct from `checkpoint`: a weight checkpoint supplies parameters; runtime state supplies ongoing neuron/synapse/delay state. Continuation validates graph/state compatibility, names, shapes, dtypes and device.

`simulate(spec, runtime_state=state)` can also supply state as a keyword argument. A non-`None` keyword state takes precedence over `spec.runtime_state`. The timestep override cannot be combined with either form of runtime state. `build` and `train` do not consume this field.

## interventions

**Type:** `Sequence[Intervention]`. **Default:** an empty tuple. Ordered `ReplaySpikes`, `DropSpikes` and `AddPoissonSpikes` objects alter emitted population spikes during simulation/inference. They do not replace ordinary neuron integration and are rejected by training. See [Spike Interventions and Replay](/api/sim/interventions) for order, seeds and validation.

### DenseSpikeReplay

A binary `(time, batch, cells)` snapshot with absolute start step, timestep and canonical payload digest. Use `DenseSpikeReplay.from_tensor` for an independent validated snapshot. See [dense replay](/api/sim/interventions#densespikereplay).

### SparseSpikeReplay

A snapshot of ordered absolute `(step, batch, cell)` coordinates plus explicit coverage dimensions and digest. Empty coordinates mean zero spikes over the covered interval. See [sparse replay](/api/sim/interventions#sparsespikereplay).

### Replay coverage and continuation

Replay must cover the complete current absolute execution window with matching timestep and dimensions. Continuation begins at `runtime_state.completed_steps`. See [coverage and continuation](/api/sim/interventions#replay-coverage-and-continuation).

### Replay files and cache checks

`save_spike_replay` / `load_spike_replay` persist and authenticate replay bytes. `intervention_identity` resolves expected policy/window metadata for cache checking. See [replay persistence and cache checks](/api/sim/interventions#replay-files-and-cache-checks) and [Inference Artifacts](/api/sim/inference-artifacts).

## options

**Type:** `Mapping[str, Any]`. **Default:** empty mapping.

Inference and compatibility options. Training controls are explicit fields described above. The top-level mapping is not a universally validated configuration schema: unknown top-level keys can be ignored. Only the keys consumed below affect direct graph handlers. CLI adapters may carry additional CLI fields here; that does not make them supported typed graph options.

### inference_overrides

`options["inference_overrides"]` is a mapping applied by simulation/inference. Supported keys are:

| Key | Value | Effect |
| --- | --- | --- |
| `duration_ms` | Positive duration aligned to graph timestep | Resample generated Poisson inputs for that duration. |
| `input_rate_hz` | Finite, non-negative rate | Replace each Poisson binding's rates with one fixed rate. The per-step probability must remain valid. |
| `projection_scales` | Mapping of projection ID to finite, non-negative factor | Scale named projection parameters after checkpoint loading. |
| `timestep_ms` | Finite, positive timestep | Recompile an immutable copy of the graph timebase and resample generated Poisson input while preserving physical duration unless overridden. |

Unknown override keys or projection IDs raise `ValueError`. Duration/rate/timestep changes require resampleable Poisson inputs and reject dense/event replay. A dataset snapshot is not a substitute for these Poisson bindings. New timesteps must also satisfy graph delay/timing validation.

Timestep recompilation rejects runtime continuation state. When using a checkpoint with a new timestep, checkpoint identity is checked against the source graph before parameters load into the effective graph. Projection scaling can be used with replay inputs. Source graph/checkpoint files are not rewritten by these request-local overrides. Metrics record requested and resolved values.

## Calling the API

The named objects below follow the same structure as Quickstart. Here, `compiled_graph` is an already compiled graph declaring a spike input named `"inputs"` with `(time, batch, 16)` axes; its graph timestep determines physical duration.

```python
from snnlab.sim import ExecutionSpec, PoissonInputBinding, simulate

poisson_input = PoissonInputBinding(
    input_id="inputs",
    steps_count=3000,
    rates_hz=(80.0,),
    seed=17,
)

execution = ExecutionSpec(
    kind="simulate",
    graph=compiled_graph,
    input_bindings=(poisson_input,),
    seed=17,
    device="cpu",
)

result = simulate(execution)
```

`build(spec)`, `simulate(spec)`, `infer(spec)` and `train(spec)` return `ExecutionResult`. `execute_request(spec)` dispatches to them using `kind` for graph execution. None of the direct simulation handlers automatically writes CLI output directories or PNGs; save the returned tensors or render them explicitly.

## Validation summary

1. Use the default graph executor (or set `executor="graph"` explicitly), a supported operation, and either compiled graph data or a bundle.
2. Cover every graph input by its exact ID, with no duplicates or overlapping binding routes.
3. Keep time/batch axes consistent; satisfy declared feature shapes, binary spike/mask rules and finite-value checks.
4. Supply all input sources through `input_bindings`. Dense/event bindings may coexist for different inputs; Poisson and dataset snapshot bindings follow the [input compatibility rules](/api/sim/execution-spec#inputbinding).
5. For training, supply a compiled recipe and exactly matching named targets, or a dataset snapshot carrying its target binding.
6. Use valid devices, the diagnostics flag and handler-specific options. Respect checkpoint and runtime-state compatibility.

Validation happens when a handler resolves the request. Frozen dataclass construction alone is not proof that a request is executable.

## Custom dynamics validation

`extension_validation="strict"` opts into diagnostic value checks. It checks custom neuron/synapse state and spikes at every step and custom surrogate derivatives during backward. Nonfinite values and nonbinary spikes raise `ValueError`; tensor type, shape, device, dtype and state keys are always checked.

`extension_validation="structural"` is the default. Use strict mode while developing custom callbacks or investigating numerical failures. Structural mode skips those step/backward value scans and binary-spike checks, avoiding their host scalar reads on CUDA. Invalid values can propagate silently in this mode: output or gradient checks alone cannot establish that intermediate states were valid. Initial state, restored runtime state, initializers, constraints, custom graph operations and training callbacks retain strict validation. Input validation and other execution paths may still synchronize. Build/run metrics record the policy; it is an execution setting, not a change to the saved graph or checkpoint format.

The same keyword is accepted by `GraphExecutor`; the CLI uses `--extension-validation strict|structural`. Surrogate definitions and autograd dispatch are resolved once per executor. Construct a new executor after changing a registration or surrogate configuration.


## GPU performance controls

`compile_mode=None` retains eager execution. `"default"` prepares separate full-graph `torch.compile` kernels for built-in LIF, ALIF, AdEx and leaky-integrator updates. Projection matrix products, timestep scheduling, delays, interventions, recordings and custom neuron/synapse callbacks remain eager. Registered custom surrogates use eager neuron dispatch to preserve their validation contract. Build metrics report `compile_mode` and `compiled_populations`. Prepared kernels capture the neuron configuration at construction; construct a new executor after changing it. Compilation is lazy: first calls, training/inference switches and new shapes can compile additional variants. Include that cost when assessing short jobs. Compiler failures on a requested compiled kernel are surfaced rather than silently falling back. Use `compile_mode=None` for environments without a compatible compiler. Compare outputs and gradients before adopting compilation for a scientific workload, since fused floating-point arithmetic can differ slightly.

`dataset_prefetch=0` preserves synchronous batch preparation. Values from 1 to 8 enable bounded lookahead for built-in dataset encoders in training, validation and dataset inference. A single worker prepares CPU batches in order with the existing per-batch seeds. CUDA uses pinned CPU buffers, a transfer stream, events and consumer-stream lifetime tracking; other devices retain synchronous transfers. Custom encoders run synchronously on the caller thread because callbacks can consume global random state. Prefetch buffers are released when iteration completes or fails. These execution controls do not alter dataset identity, generated spikes or checkpoint data order. Larger lookahead increases host and device memory use; start with 2 and measure the complete workload.

For simulation/inference, `timing_mode="synchronized"` brackets input resolution and completed execution with device synchronisation and reports `metrics["simulate_s"]`. This includes encoding, transfers and recording, but excludes model construction and checkpoint loading; `timing_scope` records that boundary. CPU requires no device fence. MPS uses its device synchronisation API. `timing_mode="enqueue"` omits these fences and reports `simulate_enqueue_s` instead: this is host elapsed time and may exclude queued accelerator work. Existing internal validation, recordings and other operations may still synchronise. `peak_python_bytes` measures Python allocations only, not GPU tensor memory.

The CLI exposes `--compile-mode default`, `--dataset-prefetch N` and `--timing-mode synchronized|enqueue`. Use `--no-diagnostics` when dense diagnostics are unnecessary. Gradient reporting copies only the final update or explicitly observed gradients, metric reporting batches host reads, and batch-loss selection snapshots only improving candidates. Selection still requires its loss read; requested gradient-norm observations still have measurement overhead.

For a complete CUDA benchmark with score/gradient checks, cold/warm timings, operator counts and allocated memory, run `uv run python benchmarks/gpu_efficiency.py --output gpu-results.json` from a repository checkout. [Benchmark source](https://github.com/eoinmurray/snnlab/blob/main/benchmarks/gpu_efficiency.py) and [Modal runner](https://github.com/eoinmurray/snnlab/blob/main/benchmarks/modal_gpu.py) are provided. The benchmark disables TF32 and separates profiling from timing. Measure your actual batch size, graph and recording policy before drawing throughput conclusions.


## Projection arithmetic and result snapshots

`projection_mode="fast"` is the default for all graph training, simulation, inference and direct executor calls. A built-in projection whose resolved numerical decay is exactly zero uses its current matrix-product drive directly, removing the previous-state multiplication/addition and their autograd work. This covers instantaneous leaky-integrator projections and positive exponential time constants whose decay underflows to exactly zero. Nonzero decays retain their recurrence. Delayed/recurrent routing, polarity and autapse masks are unchanged, and custom synapse callbacks always execute their declared equations.

`projection_mode="strict"` preserves the historical `previous * decay + drive` expression, including IEEE nonfinite propagation through zero multiplication. Fast mode can clear a stale NaN/infinite projection state when the current drive becomes finite. NaN/infinite current drives still propagate. It also removes the zero backward edge: nonfinite upstream gradients no longer propagate through that discarded dependency, and an otherwise unused leaf can receive no gradient instead of a materialized zero. Signed-zero behavior can differ. Neither mode scans values each timestep. This arithmetic policy is independent of `extension_validation`, which continues to control custom callback value checks. The CLI exposes `--projection-mode fast|strict`.

Metrics record the selected mode. Fast training protocols record `projection_mode="fast"`; absent metadata denotes historical strict arithmetic. Checkpoint resume rejects an arithmetic-policy change. Runtime-state compatibility binds fast semantics when an enabled built-in zero-decay projection is present; old states for those graphs require a strict executor. Saved graph/checkpoint/state schemas do not change. Inference retention identity also records fast mode, so preflight `retention_identity(..., projection_mode="strict")` when deliberately reusing historical strict caches.

`retain_parameters`, `retain_final_state` and `retain_runtime_state` independently control returned parameter, final-voltage and complete continuation-state snapshots. All default to `True` for existing direct/inference callers. Set all three to `False` for an output-only result while preserving named outputs, gradients, diagnostics, recordings and decisions. Omitted mappings are empty and omitted runtime state is `None`; continuation requires requesting a complete runtime snapshot. These controls do not truncate autograd or suppress the internal state needed to execute the graph. The built-in training/evaluation loop automatically omits unused per-batch snapshots. Returned training parameters follow `retain_parameters`; mandatory training checkpoints remain complete. Training returns its existing optimizer checkpoint rather than a simulation runtime state.

The CLI exposes `--no-retain-parameters`, `--no-retain-final-state` and `--no-retain-runtime-state`. Saving runtime state while omitting it fails explicitly. Include the same flags in `retention_identity` before cache reuse; default full snapshot identity retains its historical shape under strict arithmetic, and omitted snapshots are recorded explicitly. Dataset inference propagates these controls to each batch and retains global recording coordinates. Python `GraphExecutor` calls accept the retention flags per forward call and `projection_mode` at construction.

The [zero-decay benchmark](https://github.com/eoinmurray/snnlab/blob/main/benchmarks/zero_decay.py) compares a matched custom Synaptic classifier against snnTorch on identical inputs and weights. It measures controlled ablations at initial and newly trained weight states plus full MNIST training/test runs. [Modal runner](https://github.com/eoinmurray/snnlab/blob/main/benchmarks/zero_decay_modal.py) uses one L4, independent profiler passes and synchronized randomized timing repetitions.

## Input resolution helpers

Import these functions and `ResolvedDenseInputs` from `snnlab.sim`. Normal simulation/training requests perform resolution automatically. Low-level resolvers materialize inputs; use request-managed dataset batching for bounded batch encoding.

```python
class ResolvedDenseInputs:
    tensors: Mapping[str, torch.Tensor]
    protocol: Mapping[str, Any]
```

`ResolvedDenseInputs.tensors` maps graph input IDs to device tensors; `.protocol` retains resolved shapes, timing and source provenance.

### File loaders

```python
def load_dense_array_bindings(
    path: str | Path, graph: Mapping[str, Any]
) -> tuple[DenseArrayBinding, ...]: ...


def load_target_array_bindings(
    path: str | Path, training: Mapping[str, Any]
) -> tuple[TargetArrayBinding, ...]: ...


def load_event_stream_bindings(
    path: str | Path, graph: Mapping[str, Any]
) -> tuple[EventStreamBinding, ...]: ...
```

`load_dense_array_bindings` loads NPY/NPZ with pickle disabled and records file digest/source metadata. NPY requires exactly one graph input. NPZ keys normally name inputs; a single `input_spikes` array supports the historical single-input alias. Full graph shape/name validation occurs during resolution.

`load_target_array_bindings` loads NPY for a recipe with one named target, or NPZ with exactly the recipe's target names. It returns a tuple of bindings; dtype/sample checks occur during resolution.

`load_event_stream_bindings` requires NPZ coordinate arrays. A single-input file can use `steps`, `batches`, `channels`, `steps_count` and `batch_size`; multi-input files prefix each field with `<input_id>.`. It returns typed event bindings without treating absent events as missing coverage. Invalid file/key layouts fail; event coordinate validation occurs in the resolver.


The family-specific resolvers require bindings matching the graph's named inputs. They validate dimensions, dtype/value contracts and common time/batch axes, move/materialize tensors on `device`, and return `ResolvedDenseInputs`. Do not supply both dense `bindings` and `inputs` mappings. Sparse event resolution creates dense binary execution tensors; it is not a sparse execution backend.

`resolve_input_bindings` combines dense, event and Poisson sources for different inputs. Each graph input must occur exactly once across the supplied families. Source provenance and resolved timing are retained in the protocol. Seeded Poisson generation follows each binding's seed and declared graph timestep; rates must produce valid step probabilities. Caller protocol metadata does not override shape/value validation.

### Targets

```python
def resolve_target_array_bindings(
    training: Mapping[str, Any],
    *,
    bindings: Sequence[TargetArrayBinding] = (),
    targets: Mapping[str, torch.Tensor] | None = None,
    sample_count: int,
    device: str | torch.device = "cpu",
) -> tuple[dict[str, torch.Tensor], list[dict[str, Any]]]: ...
```

Returns `(targets, provenance_rows)`. Target IDs must match the recipe, with `sample_count` leading samples. Classification targets require a one-dimensional integer vector, converted to `torch.long`; custom non-classification targets accept finite real arrays, including additional dimensions. Duplicate or missing IDs and incompatible shapes/dtypes raise errors. Supply `bindings` or `targets`, not both.

## Run snapshots

Set `snapshot="runs/example"` to export the effective network, resolved execution
settings and parameter arrays just before execution. Use
`SnapshotSpec(path="runs/example", parameters=False, stage="end")` for settings
only after execution, or `stage="both"` for initial/final captures in separate
subdirectories. Supported for simulation, inference and training; build requests
reject this option. Existing snapshot files are not overwritten. See
[Run Snapshots](/api/sim/run-snapshots) for the format and re-export API.
